# GS Flow Viewer — 실행 기준 중심 흐름도 생성

현재 프로젝트의 `.gs` 코드를 분석하여 `diagrams.md`에 Mermaid 흐름도를 생성한다.

## 목적

독자는 코드를 모르는 업무 담당자다. 코드 구조나 함수 호출 관계가 아니라 다음 순서가 보이게 작성한다.

> 언제 실행되고 → 무엇을 확인하고 → 어떤 값일 때 계속되며 → 무엇을 하는가

## 절대 원칙

### 실행 기준을 값까지 표시한다

`상태 변경 감지`, `조건 확인`, `항목 처리`처럼 끝내지 않는다.

- 상태 변경 감지 → `"디자인 완료"로 변경되면 계속`
- 대상 보드 확인 → `"패키지 리뉴얼" 보드이면 계속`
- 원본 링크 확인 → `링크 있음: 계속 / 링크 없음: 담당자 알림`

### 함수 경계를 흐름의 경계로 취급하지 않는다

진입 함수에서 호출되는 판정 함수와 처리 함수 안으로 계속 들어간다. 그 함수가 참조하는 상수와 설정도 찾아 실제 업무값으로 복원한다.

예를 들어 다음 호출 구조를:

```javascript
function onChange(e) {
  if (shouldProcess(e)) {
    processItem(e);
  }
}
```

다음처럼 쓰지 않는다.

```text
변경 감지 → 처리 대상 확인 → 항목 처리
```

`shouldProcess()`와 `processItem()` 내부, 그 안에서 참조하는 상수까지 따라가 최종 의미를 다음처럼 펼친다.

```text
상태가 "디자인 완료"로 변경됨
        ↓
"패키지 리뉴얼" 보드인가?
   ├─ 아니오 → 처리하지 않음
   └─ 예
        ↓
담당자가 지정되어 있는가?
   ├─ 아니오 → 처리하지 않음
   └─ 예 → 서브아이템 생성
```

함수명과 변수명은 분석할 때만 사용하고 최종 노드에는 노출하지 않는다.

### 모든 중요한 분기를 실제 업무 분기로 번역한다

각 `if`, `switch`, `early return`에서 다음을 확인한다.

- 무엇을 확인하는가
- 어떤 값과 비교하는가
- 충족되면 무엇을 하는가
- 충족되지 않으면 무엇을 하는가

`조건 충족?`, `대상인가?`, `유효한가?`처럼 비교값을 숨기지 않는다. AND/OR 조건이 실행 경로를 바꾸면 별도 판단 노드로 나눈다.

### 트리거의 실제 발동 조건을 표시한다

Webhook, 시간 트리거, 메뉴 실행, API 요청 등 진입점을 찾고 다음을 표시한다.

- 무엇이 변경되거나 요청되는가
- 어떤 보드·시트·항목이 대상인가
- 어떤 값으로 변경되어야 계속되는가
- 추가 필수 조건이 무엇인가

### 상수와 설정을 업무 의미로 해석한다

보드 ID, 컬럼 ID, 상태 상수의 선언과 사용처를 따라 실제 의미를 찾는다.

- `TARGET_BOARD_ID` → `패키지 리뉴얼 보드`
- `STATUS_DONE` → `"디자인 완료" 상태`
- `COL_17` → `원본 파일 링크`

코드에서 실제 의미를 확인할 수 없으면 추측하지 않고 `설정된 대상 보드`, `설정된 완료 상태` 수준으로 표시한다.

### API 호출이 아니라 업무 결과를 쓴다

- Monday API 호출 → 서브아이템 생성
- 데이터 갱신 → 담당자 정보 복사
- 메시지 전송 → Google Chat에 원본 링크 누락 알림

## 노드 작성 규칙

메인 흐름은 행동과 핵심 조건 1~2줄만 유지한다.

```text
상태 변경 감지
"디자인 완료" → 실행
```

```text
패키지 리뉴얼 보드인가?
일치 → 계속
```

```text
서브아이템 생성
제품명 · 담당자 · 링크 복사
```

```text
처리하지 않음
대상 상태가 아님
```

```text
담당자에게 알림
원본 링크 없음
```

실행 여부, 행동 분기, 처리 중단, 외부 시스템 변경, 사용자 알림에 영향을 주는 조건을 우선 표시한다. 단순 방어 코드와 내부 구현 세부사항은 생략할 수 있다.

## Viewer 출력 계약

1. 첫 Mermaid 섹션은 `## 전체 구조`
2. 이후 실제 `.gs` 파일마다 상세 섹션 하나
3. 상세 제목은 내부 연결용 실제 경로와 비개발자용 업무명을 함께 기록
4. 형식: `## <상대 경로>/<파일명.gs> | <업무명>`
5. 전체 구조 노드는 `<업무명>`을 사용
6. 사이드바 파일 목록에는 실제 파일명을 표시하되, 전체 구조·상세 제목·흐름 노드에는 파일명·함수명·변수명을 표시하지 않음
7. Mermaid `flowchart TD` 사용
8. 상세 흐름에서는 파일과 함수 경계를 무시하고 실제 실행 결과까지 연결
9. 미사용 코드는 업무명 뒤에 `· 미사용` 표시
10. 현재 소스에 없는 섹션은 제거

## 분석 절차

각 진입점마다 다음 표를 내부적으로 완성한 뒤 Mermaid를 작성한다.

1. Trigger — 무엇이 실행을 시작하는가
2. Trigger condition — 정확히 어떤 값일 때 실행되는가
3. Decisions — 어떤 판단을 하는가
4. Criteria — 무엇을 어떤 값과 비교하는가
5. Branches — 충족·미충족 시 어디로 가는가
6. Actions — 무엇을 생성·변경·복사·전송하는가
7. Stops — 어떤 경우 아무것도 하지 않는가
8. Notifications — 누구에게 무엇을 알리는가

호출된 다른 함수와 파일, 상수, 설정을 따라가 2~8의 실제 값을 확인한다.

## 최종 검수

각 흐름을 보고 다음 두 질문에 답할 수 있어야 한다.

- 왜 지금 실행됐는가?
- 왜 이쪽 분기로 갔는가?

답할 수 없으면 해당 호출 경로와 상수 정의를 다시 확인한다.

완료 후에는 다음을 검증한다.

- 실제 `.gs` 파일과 상세 섹션 수·경로 일치
- 전체 구조의 모든 업무 노드가 상세 화면으로 이동
- 모든 Mermaid 블록 문법 통과
- 사이드바·전체 구조·상세 제목에 파일명과 함수명이 노출되지 않음
- 실제 브라우저에서 대표 흐름의 분기 라벨과 중단 경로 확인
